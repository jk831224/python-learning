帶學習者定義專案契約。專案想法：$ARGUMENTS

Claude 的角色是**提問者與審查者**：提出問題、給選項與建議，所有決定由學習者做。每輪只問一個區塊，等回答再往下。

1. **目的**：這個工具解決什麼痛點？誰用？做完之後原本的工作流程哪裡變輕鬆？
2. **輸入**：資料從哪來、長什麼樣。請學習者提供一份範例檔或描述欄位；有範例檔就讀它。
3. **輸出**：要產出什麼（檔案、報表、畫面上的文字），長什麼樣。
4. **資料結構**：Claude 依輸入與輸出起草 DBML（表、欄位、型別、是否必填、note 寫範例值），貼在對話裡請學習者審。說明這就是**API 契約**的雛形。
5. **狀態**：資料會不會在幾個狀態之間轉換（例：草稿 → 已確認 → 已付款）？會的話，Claude 起草 Mermaid 狀態圖請學習者審，並問「每個狀態能不能回頭」。不會就略過。
6. **驗收條件**：請學習者用 Gherkin 寫 Feature 與 Scenario。學習者寫完後，Claude 審查：
   - 每個 Scenario 的 Given/When/Then 是否具體到能寫成測試
   - 缺了哪些**邊界條件**（空的、缺欄位、格式錯、逾時），以「如果 X 發生，應該怎樣？」的問句提出，由學習者決定要不要補
   - 至少一個一般情況、兩個邊界條件
7. **不做的事**：明確列出這次範圍外的功能。

每個區塊回答後，用一句話點名它對應四個概念中的哪一個。

所有區塊都有共識後，把完整草稿貼在對話裡，請學習者回覆「確認」。確認後建立 `projects/<專案英文名>/`：

- `SPEC.md`：目的、輸入、輸出、不做的事；有狀態圖就放在這裡。標題下注明確認日期。
- `features/<功能英文名>.feature`：學習者寫的 Gherkin，逐字照收，只修正學習者同意的部分。
- `schema.dbml`：審過的資料結構。

接著：

- 更新 `PROGRESS.md` 的「目前專案」。
- 告訴學習者下一步：說「開始做」，進入中層（先寫 step definitions，確認 red）。

完成條件：學習者明確回覆「確認」，三個契約檔都已建立，`.feature` 至少一個一般情況、兩個邊界條件。
