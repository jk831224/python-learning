# 學習觀念

整理自一位資深工程師給學習者的建議（已改寫，不含原文與人名）。Claude 規劃學習路線、出題、或回答「為什麼要學這個」時參照本檔。

## 目標導向

- 沒有想解決的問題，讀教材只會想睡。先找到「我想做出什麼」，再反推需要哪些知識。
- 不必逐章啃教科書，但每學一樣東西都要知道它為什麼需要。
- 選擇比努力重要：努力本身不是成果，要明確知道自己缺什麼，主動去拿。
- 深度看需求決定。演算法的數學在多數工作中用不到。

對 Claude 的意涵：每一題練習都要能說出「這是為了專案的哪一步」。

## 四個概念

這四個不是語法，是看懂一個系統的思考框架。

| 概念 | 在問什麼 | 例子 |
|---|---|---|
| **資料流（Data Flow）** | 資料從哪裡進來、經過哪幾層、每層做了什麼、最後落在哪 | 使用者在瀏覽器按下送出 → 請求送到後端 → 經過驗證、商業邏輯 → 寫進資料庫 |
| **狀態機（State Machine）** | 東西有哪些狀態、能從哪個狀態轉到哪個、能不能回頭 | 付款付到一半斷線或逾時：能回去重付，還是必須重新下單？ |
| **API 契約（API Contract）** | 兩方約好交換什麼格式、哪些欄位、什麼型別；格式轉換的坑在哪 | 前後端約定「訂單」的 JSON 有哪些欄位、日期用什麼格式 |
| **邊界條件（Edge Cases）** | 怎樣算合法、怎樣算壞掉、壞掉時怎麼應對 | 空檔案、欄位缺漏、數字是負的、網路逾時 |

背後還有一層「資料結構怎麼存」，依需要深入。

## 三明治協作流程

與 AI agent 協作時，不要直接說「幫我做一個購物車」。分三層：

1. **頂層（人定契約）**：和 agent 討論並鎖定資料結構（用表格或 JSON 寫出有哪些欄位、什麼型別）與驗收條件（Given / When / Then）。
2. **中層（agent 執行閉環）**：要求 agent 先依規格寫測試、確認測試失敗，再寫實作直到測試通過，過程中不修改測試標準。
3. **底層（人審邊界）**：人不逐行讀實作，而是要求 agent 說明處理了哪些邊界條件、某個依賴壞掉（例如 API 逾時）時會怎樣，並親自操作成品或看測試報告驗收。
